# Gemini Live with Pipecat Flows: a browser prototype

The service uses the real `pipecat.flows.FlowManager` from Pipecat 1.14.0 and a separate executor `GeminiLiveFlowManager`. Speech is generated by Gemini Live with the standard voice Puck. There is no separate STT or TTS in this mode.

In the form choose **"Flows + Gemini Live — проверка завершения"** (Flows + Gemini Live — ending check), prepare the task and start a conversation. The previous Gemini Live mode is available for comparison. A new task fixes the chosen mode, facts, instructions and prompt version. Only the selected messages are passed from AnyMsg; a test with your own facts does not require reading correspondence.

The graph contains the conversation, summing up, waiting for an answer to the offer to finish, and the farewell. All seven tools are declared at connection. The transition is recorded before the tool result is sent; the result contains the current stage, instructions, allowed tools and the revision number. A transition does not reconnect Gemini and does not start the model again. The conversation tools use NON_BLOCKING/WHEN_IDLE: after saving, the model can ask the next question. Quiet saving means there are no service remarks about every note; this manner is set by the prompt.

The scheduling parameter is set in the field `FunctionResponse.scheduling`, not only inside the JSON of the result; a regression checks the real serialization of the installed Google SDK. The adapter keeps support for `SILENT` for explicitly background actions, but `record_answer` and `finish_task` do not enable it: in a live check it suppressed the next question and left the model waiting for new speech. According to the [Live API documentation](https://ai.google.dev/gemini-api/docs/live-api/tools), `SILENT` keeps the result for further discussion, and `WHEN_IDLE` allows continuing after the current answer. The manner of speech is checked by ear.

For transcription, Flows passes `language_codes` in both transcription settings: RU → `ru-RU`, EN → `en-US`, ID → `id-ID`. This is a hint to the recognizer, different from the model instruction to speak the chosen language. [Google recommends language hints](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/live-api/best-practices#set_transcription_language_code); they do not guarantee accuracy. The pre-connection hook is bound to Pipecat 1.14 and is applied again on reconnect; the serialization of all three variants was checked through the installed Google SDK. A separate Gemini Developer API connection with `ru-RU` passed without sending audio. A by-ear check of accuracy is still necessary.

Ending is protected by the server:

- Collected fields and `finish_task` save the result but do not end the call.
- A pending owner decision does not keep the person on the line after a fresh clear farewell. If the model specified `completed`, the server returns the actual reason `needs_owner`; the request stays open, and this does not authorize any terms. A repeat call is not promised and is not started automatically.
- `propose_closing` stays an optional internal step. For ending, a fresh farewell or an unambiguous answer to the immediately preceding question is enough: «нет, спасибо» ("no, thanks") after «что-то ещё хотите обсудить?» ("anything else you'd like to discuss?") does not require a second agreement. A short «да» ("yes") after a question about additional topics, a denial of a surcharge and an answer to a question about a new story do not allow hanging up.
- The answer is checked as a whole, taking the question into account: «нет, у меня нету» ("no, I have none") after a question about additional topics and «хотелось бы» ("I would like to") after an offer to finish are acceptable. A polite suffix does not change the meaning; a continuation «но я ещё расскажу» ("but I will tell more") is not discarded. This is a limited RU / EN / ID grammar, not a universal intent classifier; new live cases should be saved into the regression.
- An explicit farewell, a refusal or an inability to talk are checked on the last utterance. A late save result does not force asking again about ending after an explicit farewell. The quote is mandatory in the tool schema. An ambiguous server refusal requires new speech before a retry.
- For an ordinary ending, differences of case and punctuation in the quote do not create an additional agreement; the words and their order must match the last transcription. The original record and the quote passed by the model are stored separately. Substituted words, a translation of an erroneous transcription and an old farewell do not allow hanging up. Quote checking for saving facts is not changed by this.
- New speech immediately revokes the permission. An old successful tool result does not restore it.
- If the last completed assistant utterance already ended with a short farewell and the person answered with an explicit farewell, the server returns `farewell_already_said=true` and a reference to that utterance. A second assistant answer is not needed. Unfinished, interrupted or old text does not replace a farewell; a resumed story cancels hanging up.
- Hanging up waits for the end of generation, playback and 400 ms of silence after the assistant's sound. If the exchange of farewells has already taken place, a new farewell utterance is not required; otherwise the playback of the new farewell is checked. The permission is checked again. If the conditions are not met within 30 seconds, the permission is revoked and the connection stays open.

The stand shows stages, transcription, tool calls, saved answers and the delay from the end of speech to the start of the received sound. This is an RMS-based estimate in one browser: the greeting and answers with speech overlap are excluded. A p95 over several answers is not a stable benchmark. The HTML audio player starts WebRTC playback, a separate analyzer measures the same stream without a second output to speakers.

The prototype supports a prepared graph, state/placeholders, handlers, checking tools by stage and the APPEND strategy. Runtime replacement of tools, role messages, RESET, built-in `tts_say`/`end_conversation` and a separate cloned TTS are rejected. Existing prompt fixes of the previous mode are not carried over here automatically. Internal SDK 1.14.0 hooks are used: when Pipecat is updated, the contract and audio tests must be repeated. This is a local adaptation, not a declaration of full upstream compatibility of Flows with the Live API.

The mode is allowed only for the browser. Telegram, Twilio and SIP keep the previous executor until a separate call verification. The prototype has not proved the absence of a disconnect under any network fault: the checks manage a normal ending, and a transport break remains a separate cause.

Minimal check:

1. Give two answers, then correct one; check `record_answer` and the summary.
2. After the answers are saved, say «подожди, я ещё не закончил» ("wait, I'm not finished yet") and continue the story. The connection must stay open.
3. After the offer to finish, ask a new question, then answer «да» ("yes") to a question on the new topic. This must not end the call.
4. Say an explicit «спасибо, до свидания» ("thank you, goodbye"); check one farewell utterance and a normal hang-up.
5. Interrupt the farewell with new speech; check the revocation of permission. Repeat in Russian, English and Indonesian.
6. If the assistant has already said goodbye, answer «до свидания» ("goodbye"): the connection must end without another assistant farewell.

«Нет, спасибо, до свидания» ("No, thank you, goodbye") is also an explicit farewell: a negative answer before it does not require another agreement. This is checked on RU / EN / ID with input fragments before the transcription is finalized. A negation of the farewell itself and a continuation of the story («не до свидания», "not goodbye"; «подожди, я ещё расскажу», "wait, I will tell more") do not give permission to hang up.

For a separate local stand run from the service folder:

```sh
VOICE_PORT=13846 VOICE_DATA_DIR=../../.local/voice-flow-browser/data uv run python app.py
```

Open `http://127.0.0.1:13846/`. The Gemini key is kept in the memory of this process; after a restart it must be connected again. Texts and results are saved in a private data folder, the service does not record the source audio.

## Diagnosing disappearing sound

"Диагностика звука" (Sound diagnostics) shows WebRTC aggregates during a conversation and saves them in `metrics.audio_health` before closing the connection. Measured: lost and dropped packets, jitter, average buffer, concealed audio samples (including silence), browser timer delays and the playback state. Unavailable statistics stay unknown. A limited internal hook `transport.pc` of the SmallWebRTC 1.10.8 client is used; check it again when the SDK is updated.

The event `inbound_audio` (every channel, README "Telegram audio diagnostics") counts the frames received from the caller after the transport input. The event `provider_audio_health` saves the number, total duration and frequencies of PCM fragments, as well as the intervals of their arrival from Gemini within utterances. Audio, network addresses and device identifiers are not saved in these counters. The counters do not replace listening: a successful text dialogue or the presence of an audio signal does not yet prove continuous sound. The interval between the first and last PCM fragment is not the response delay from the end of the person's speech.

The `runtime` field of the same event measures server loop delays and the intervals of audio write completion in the Pipecat output processor. Up to 12 relative marks show delays longer than 80 ms; a pause after the end of an utterance is not counted as a write delay. This is an observation of write completion, not of the time an RTP packet was sent: the queue, an empty source and actual playback need to be compared with the other counters.

With a large share of concealed stream, the interface warns about gaps. If `silentConcealedSamples` is available, concealed silence is excluded from the warning threshold; with an unknown value the gaps are marked as possible. The percentage without concealed silence is counted from the whole stream, not only from speech. A connection break is shown separately from a normal ending. A single client counter cannot establish whether the generator, the server scheduler, the network or the browser is to blame. For diagnosis, compare both sides and compare one scenario with the same microphone, audio output and computer load. The value of concealedSamples is defined in the [W3C specification](https://www.w3.org/TR/webrtc-stats/#dom-rtcinboundrtpstreamstats-concealedsamples).
