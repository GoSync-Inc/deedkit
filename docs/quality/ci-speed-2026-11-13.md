## Local safe speedup and remaining costs

`test_production_session.py` set the attach poll interval to zero but kept the
real 120 s monotonic deadline. Three negative cases consumed 120 s each, busy
polling. Its synthetic host now uses the existing `Clock` helper, initialized
from the real monotonic epoch to retain other deadline comparisons. Each virtual
sleep advances that host only. The production 120 s bound, 5 s interval, polling
implementation and existing assertions are unchanged. An added regression checks
all 24 polls before timeout and success at 115 s. The final weight for this module uses
the actual GitHub-hosted post-change JUnit measurement: 0.891 s for 43 cases,
versus the two-run 360.6815 s median for 42 cases before the extra regression. Tests and real providers never interact.

The diagnostic run additionally measured 260.55 s of setup phases above 0.1 s
across verify and shards 2, 3 and 5 (1,560 setup records), and 40.43 s of teardown
above 0.1 s (84 records). These are partial-suite lower bounds, not per-fixture
exclusive costs. The largest printed setup was a gateway container fixture at
4.91 s; repeated compact-read case setup reached 0.96–1.12 s each. Profiling
individual setup operations is needed before changing fixture scopes.

The balance regression retains its 10% maximum-over-mean assertion and test ID,
using the current fixture instead of the October snapshot. Both regressions failed
before the fixes. The October measurement file remains available as history.

## Capacity, boundaries and next bottleneck

Organization API reports `GoSync-Inc` plan `team` (2026-11-13). GitHub documents
[60 concurrent standard hosted jobs](https://docs.github.com/en/actions/reference/limits#job-concurrency-limits-for-github-hosted-runners).
Each sampled run has 26 expanded jobs, of which 21 ran and five skipped;
an image-affecting PR can additionally run the nine image build jobs. The final plan adds two shard jobs: 28 expanded jobs (23 executed) for a
comparable PR, or 32 executed when all nine image targets run. This stays below
the 60-job plan limit for one run. The limit
is organization-wide; simultaneous runs still compete for it.

No required check, seven `anymsg-ci::*` identities, ruleset, selection algorithm,
PR/queue/main reuse logic, permission or production setting changes. Evidence
assembly, dependencies and final job-result requirements all include shards 10
and 11, with the same report/outcome/SHA validation as shards 2–9.
Change path: AUTO (timing data, shard parallelism, synthetic test clock and
isolated query-plan statistics; no owner authority or section 2 gate changes).

After balancing, expect verify and runner/setup variance to bound the run.
Verify's calendar step is 129/135 s and its isolated backup restore 70/59 s;
native normalizer build is 45/39 s and govulncheck 21/23 s. A follow-up can move
calendar and isolated backup proof to independent jobs while retaining
`checks / verify` as an aggregate and joining their exact-SHA reports into the
same evidence. Calendar alone offers at most roughly two minutes of serial
work; actual wall saving depends on added setup and the Python tail. Retain
full result checks, missing-report failures and reuse compatibility when doing so.

Local infrastructure findings: installed `gh` 2.46 has no `pr checks --json`,
which the harness wait helper assumes and silently turns into an empty check
list; use the Actions run watcher plus explicit GraphQL merge/queue state for
this task. The uninstrumented Go menu-shape slow-scan calibration also exceeds
its configured row/disk cap on fast Ryzen (400k rows scan in about 14 ms, versus
a 250 ms target). Neither native tests nor the harness are modified in this PR.
